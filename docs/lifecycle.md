# 30단계 프로젝트 이력 검증

전체 기획이 크게 바뀌어도 원문, 재귀 구성, 정확한 Revision 재사용, 의미 파생, 실행 근거와 당시 판단을 보존하는지 실제 Rust API와 Neo4j로 검증한다. 입력 문서는 `examples/lifecycle_30/plan_v1.md`, `plan_v2.md`, `plan_v3.md`다.

## 시나리오

공통 컨셉은 “AI가 근거를 모아 제안하고 사람이 채택한다”이다. 제품은 고객 문의 지원 → 운영 장애 분석 → 사내 지식 검토로 전환한다. FE, BE, Infra, ML, DL, LLM 여섯 역할을 각각 Schema/Core/Idea와 사용 위치의 역할로 표현한다.

| 단계 | 사건 | 확인할 내용 |
|---|---|---|
| 1 | 최초 전체 기획 v1 | 원문 캡처, Project 아래 여섯 Schema와 재귀 Core/원자 Idea |
| 2 | 전체 기획 v2 | 같은 Revision 재사용과 새 의미 파생을 구분, 과거 루트 보존 |
| 3–20 | 여섯 역할 × 실제 실행 세 건 | 코드·데이터·모델·설정 참조, 결과 파일·해시, 관측·평가 기록 |
| 21–26 | 역할별 세부 기획 변경 한 건 | 파생 계보, 선택한 경로 교체, 다른 경로의 고정 Revision 보존 |
| 27 | 변경 후 유사 아이디어 검색 | 기대/제외 ID, 엄격한 역할 필터, 과거 지식 시점 검색 |
| 28 | 늦게 수집한 과거 관측 | 발생 시각과 시스템이 알게 된 시각을 분리 |
| 29 | 전체 기획 v3 | 재사용·추가 파생, 새 범위의 목표와 기준선, 이전 평가의 범위 불일치 |
| 30 | 전체 중간 상태 재조회 | 모든 체크포인트의 구성·시간 경계·검색·근거 재현 |

역할별로 실행 세 건과 세부 변경 한 건, 총 네 건을 기록한다. 상위 제품 목표와 작은 기술 실험의 완료를 구분한다. DB에 실험 성공을 기록했다고 전체 제품 기능을 구현했다고 보지 않는다.

## 실행 범위

`tests/lifecycle_workloads.py`는 Python 표준 라이브러리만 사용하는 작은 실행기다. FE의 HTML escaping/역할 필터/시간 정렬, BE의 입력 검증/멱등성/CAS 상태 모형, Infra의 실제 파일 저장·복구와 배포 설정 모형을 실행한다. 이 중 모형 검증은 실제 서버 동시성·프로세스 장애 시험을 대신하지 않는다. 실제 idea_db 프로세스와 저장소 검증은 Docker 하네스가 별도로 수행한다.

ML은 고정 난수의 합성 데이터로 로지스틱 분류기를 학습하고 분포 변화·확률 보정을 측정한다. 학습/보정/최종 평가 집합은 분리한다. DL은 작은 2층 MLP를 CPU에서 실제 학습하고 입력 오류·분포 변화에 따른 성능 저하를 측정한다. LLM은 프롬프트 변경, 구조화 응답 검증, 허용된 근거 ID 검증을 실행한다. LLM 추론 호출은 없으며 실제 모델의 답변 품질을 검증했다고 주장하지 않는다. 의도적으로 거절해야 하는 입력과 기대한 실패 결과도 성공 관측과 구별해 보존한다.

검색은 고정된 질의·기대 ID와 결정적 텍스트 특징을 사용한다. 이는 검색 경로, 역할/시간 필터, 기존 아이디어 연결의 기능 검증이다. 실제 임베딩 모델의 의미 검색 품질이나 실사용 자료에 대한 일반화 성능은 별도 평가가 필요하다.

## 시간의 의미

시나리오의 날짜·시간은 2026년 8월의 합성 사건 시간이다. 서버의 `recorded_at`과 `seq`는 실제 실행 시각과 커밋 순서를 그대로 사용한다. 과거 사건을 늦게 기록하는 경우도 포함하며 서버 시계를 조작하지 않는다. 이 fixture는 체크포인트를 `known_at`으로 정확히 나누기 위해 커밋 사이에 짧은 간격을 둔다. API 전체가 밀리초 시각의 유일성을 보장한다고 가정하지 않는다.

- `known_seq`와 그에 대응하는 `known_at`은 동일한 당시 지식 상태를 반환해야 한다.
- 공식 구성은 `published_at` 직전/정각/직후와 같은 순간을 나타내는 UTC·지역 오프셋에서 일관되어야 한다.
- 미래 관측뿐 아니라 그 관측을 근거로 한 평가도 이전 `effective_at` 조회에 나타나면 안 된다.
- 구성이나 목표 범위가 달라지면 과거 평가를 현재 목표 충족으로 자동 승계하지 않는다.
- 컨테이너 강제 종료 후, 빈 볼륨 복원 후에도 같은 30개 체크포인트를 읽기 전용으로 다시 검증한다.

## 실행과 결과

```sh
make lifecycle-check
# 결과 디렉터리를 지정하려면 존재하지 않는 경로를 사용한다.
IDEA_DB_REPORT_DIR="$PWD/test-results/lifecycle-example" make lifecycle-check
```

Docker와 호스트 Python 3이 필요하다. 하네스는 고유 이름의 임시 컨테이너·볼륨과 임시 포트만 사용하고 종료 시 정리한다. `report.json`, `report.md`, 전체 `export.json`, 실행 산출물은 결과 디렉터리에 남는다. `deployment-checks.json`은 강제 종료/재시작, 빈 볼륨 복원, 두 번의 이력 재검증, 필수 프로세스 상실과 정상 종료가 모두 통과한 뒤에만 생성한다. 실패는 0이 아닌 종료 코드로 반환한다.

이미 준비한 전용 검증 DB에서는 다음 명령으로 실행할 수 있다. 쓰기 실행은 테스트 Project를 추가한다. 읽기 전용 재검증은 보고서의 ID·시각을 이용한다.

```sh
python3 tests/lifecycle.py --base-url http://127.0.0.1:18080 --output-dir test-results/manual
python3 tests/lifecycle.py --base-url http://127.0.0.1:18080 --verify-report test-results/manual/report.json
```

Artifact의 JSON 결과는 호스트에 남고 DB/export에는 URI와 해시가 들어간다. 전체 복구 자료를 옮길 때는 export와 실행 산출물을 함께 보존해야 한다. 생성 결과는 `.gitignore`의 `test-results/`에 보관하며, 소스와 재현 명령은 Git에 포함한다. 최신 실제 실행 결과는 `docs/validation.md`에 기록한다.
