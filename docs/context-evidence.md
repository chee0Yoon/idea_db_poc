# 원자화·방향·문맥·DB 무결성 실험

2026-09-07 · 구현/통합: Main · 검토: Grok 4.6, Fable 5.1

현재 방향은 **원문과 그 원문을 해석한 원자, 사용 위치의 목적, 방향 변경 및
근거를 함께 보존하는 DB**다. 로컬 AI 클라이언트가 의미를 분해하고 검토하며,
MCP가 구조 검증·로컬 임베딩·적용을 연결한다. Neo4j의 저장 성공은 원자화의
의미적 타당성이나 목표의 실제 달성을 보증하지 않는다.

이번 결과는 원자만 모으면 문맥이 좋아진다는 가정을 지지하지 않는다. 원자를
현재 목적과 다시 연결하면 방향 질문과 역할 간 연결에 도움이 되지만, 좁은
예산에서 부모 설명을 무조건 붙이면 필요한 원자가 잘린다. 원문도 계속
보존하고, 질문과 남은 분량에 맞게 필요한 문맥만 선택해야 한다.

## 어떤 근거를 만들었는가

| 층 | 입력/실행 | 실제로 확인한 것 |
|---|---|---|
| 모델 출력 | 같은 한국어 반례 12개를 Grok/Fable 로컬 ACP 클라이언트에 전달 | 출력 형식, 인용 보존, 오류와 수정 비용의 실제 사례 |
| 입력 경로 | 검토한 24개 사례 → MCP preview/review/apply → Ollama → Neo4j | 원문/coverage ledger 48개, Idea 52개, 미확정 Candidate 4개 보존 |
| 문맥 실험 | 방향 3개 × 역할 6개, 질의 39개, 실제 어휘/하이브리드 검색 | 같은 바이트 예산에서 필요한 원문 근거가 남는지 |
| 의미 반례 | Unicode/출처/숫자/부정/조건 등 10개 probe | 구조적 거절과 의미 검토의 한계를 구분 |
| 무결성 | 실제 Neo4j export와 관계 대조, 강제 재시작, 빈 DB 복원 | 최종 1,079개 레코드·347개 Revision·478개 CONTAINS 관계 일치 |
| 기존 회귀 | 수용 13개, MCP intake 12개, 30단계 lifecycle | CAS·멱등성·원자적 거절·시간 조회·복구 유지 |

실제 생성 추론은 해당 제공자에서 실행했다. 로컬에서 실행한 모델은 임베딩용
`embeddinggemma:300m`이며, 생성 추론까지 온디바이스로 수행했다는 뜻은 아니다.
모델 출력은 [검토된 fixture](../examples/evidence/model-responses-reviewed.json)로
보존해서 추가 유료 호출 없이 MCP 경로를 재실행할 수 있다.

## 원자화가 가능한가

Grok 첫 응답은 JSON 형식을 통과했고 12개 문단을 26개 단위로 나눴다. 인용
문자열 오류는 0개, 공백을 제외한 원문 문자 인용 범위는 평균 99.87%였다.
다만 “둘 중”, “해당 문장”, “이 장애”처럼 부모 문맥 없이는 불분명한 단위가
있다. 이 수치는 독립적인 원자성이나 사실 정확도 점수가 아니다.

Fable 첫 ACP 응답은 JSON 객체 두 개가 이어진 형태라 엄격한 파싱에 실패했다.
“v1은 채택되지 않았다”는 원문에 없는 주장도 덧붙였다. 수정 요청에서 그 주장은
사라졌지만 전달된 결과에는 다시 두 객체가 있었다. Main이 두 내용을 비교한 뒤
두 번째 객체를 명시적으로 선택했다. 결과는 30개 단위, 인용 문자열 오류 0개,
원문 문자 인용 범위 평균 99.19%다. 이는 **수정·수동 검토 후 결과**이며 첫 응답
성공으로 계산하지 않았다. 중복 전달이 모델 또는 어댑터/후처리 중 어디서 생겼는지는
분리 검증하지 않았다.

검토된 출력의 원문은 부모 Core에 남기고, 확정하지 않은 사항은 Candidate로
보존했다. Grok Idea 24개/Candidate 2개, Fable Idea 28개/Candidate 2개가 실제 MCP
미리보기와 적용을 통과했다. 미리보기의 본문이 제출본과 같은지 직접 비교했고,
적용 후 모든 Idea에 임베딩이 있으며 후보가 구성에 섞이지 않는지 확인했다.
모델이 내놓은 “accepted”를 공식 목표 충족이나 관측값으로 바꾸지는 않았다.

따라서 이번 사례는 **원문·부모 문맥·보류 상태·클라이언트 검토를 포함한 구조화가
실행 가능함**을 보여준다. 모든 문서가 자동으로 정확히 원자화된다는 증거는 아니다.
정확한 인용만 있어도 재서술 본문에 근거 없는 주장이 추가될 수 있다.

## 문맥에 도움이 되는가

입력은 고객 문의 지원 → 운영 장애 분석 → 사내 지식 검토의 세 방향이다.
FE/BE/Infra/ML/DL/LLM 각 역할에 핵심 문장 3개와 관련 있지만 질문의 답이 아닌
방해 문장 6개를 넣었다. 하이브리드는 역할별 9개 원자 중 상위 3개를 검색한다.
문서 대조군은 역할별 문서 1개이므로 문서 선택 난도를 측정하지 않는다.

동일한 MCP 검색 결과를 다음 5가지 방식으로 포장했다. 식별자·역할·종류 라벨도
예산에 포함했다. 예산은 256/512/1,024 UTF-8 바이트이며 모델 토큰 수가 아니다.

- 원문: 선택 역할의 현재 문서 앞부분. 문서 내 문장 위치에 영향을 받는다.
- 원자 목록: 검색 상위 원자 본문.
- 원문 주변: 같은 원자를 검색 시작점으로 삼아 현재 원문의 앞뒤 문장을 추가.
- 부모 설명: 같은 검색 결과에 현재 사용 위치의 부모 Core 설명을 추가.
- 부모+의존: 부모 설명에 DB에 명시적으로 저장된 역할 간 의존을 추가.

지표는 **질문에 필요한 원문 근거가 전부 온전하게 들어 있는 비율**이다. 잘린
조건문에는 완전한 근거 점수를 주지 않는다. 라벨은 채점에서 제외했다. 원문에
여러 필요 사실이 실제로 포함되어 있으면 모두 인정한다. 이는 검색된 원자 ID의
Recall@k나 LLM 답변 정확도가 아니다. 원문·부모 설명의 정당한 근거를 ID가 다르다는
이유로 0점 처리하지 않았다. 기존 `required_fact_precision`은 비교 지표에서 제거했다.

**최종 하이브리드 결과, 512바이트:**

| 방식 | 단순 조회 18개 | 목적/방향 포함 18개 | 역할 간 연결 3개 |
|---|---:|---:|---:|
| 원문 | 100% | 100% | 0% |
| 원자 목록 | 100% | 0% | 0% |
| 원문 주변 | 66.7% | 16.7% | 0% |
| 부모 설명 | 77.8% | 77.8% | 0% |
| 부모+의존 | 77.8% | 77.8% | 100% |

256바이트의 단순 조회에서는 원자 목록이 66.7%, 부모+의존이 16.7%였다.
부모 설명이 뒤의 중요한 원자를 밀어내는 반례다. 1,024바이트의 목적/방향 질문은
원문·원문 주변·부모 설명 모두 100%, 원자 목록은 0%였다. 원자에 목적을 연결하는
효과가 있지만, 그 효과 대부분은 이번 자료의 부모 설명에서 나온다.

역할 간 질문은 엄격한 역할 필터를 통과한 직접 결과만으로는 상대 역할의 근거에
도달할 수 없도록 설계했다. 의존 링크 1종의 도움이 확인된 것이며, 다른 36개와
합쳐 “그래프가 더 정확하다”는 평균을 만들지 않았다. 원문 대조군도 512바이트에서
목적/방향을 잘 보존하므로 그래프가 원문보다 항상 낫다는 결론은 성립하지 않는다.

질의 39개는 6개 역할 주제를 세 루트에서 반복하므로 서로 독립인 표본이 아니다.
방해 후보 추가와 대조군 보완은 첫 결과 및 리뷰를 본 뒤 이루어졌다. 각 실행 전에
입력/질의를 파일로 고정했지만, 독립된 사전등록 실험이나 유의성 검정으로 해석하지
않는다. 초기 3후보 실행과 이후 9후보 실행은 별도 보존했다. 실제 모델의 답변
정확도·사용자 수정 시간·대규모 문서 검색 성능은 측정하지 않았다.

## DB 무결성과 의미적 일치의 차이

최종 격리 DB의 레코드 1,079개, Revision 347개, head 9개, receipt 86개를 검사했다.
원문 앵커, 참조 종류, 순환 없는 구성, 목표/평가의 정확한 사용 경로, 기준선,
근거 cutoff, head의 Project 일치, export digest를 검증했다. 실제 Neo4j의
CONTAINS 478개도 from/to/slot/roles를 전체 비교했다. 강제 재시작과 빈 DB 복원 후
같은 export 내용·digest·모든 과거 체크포인트 및 관계를 다시 확인했다.

메인 DB는 **474개 레코드, 114개 Revision, head 2개, receipt 33개**, CONTAINS
150개를 읽기 전용 검사했다. 오류 0개이며 기존 데이터와 컨테이너를 변경하지 않았다.

Unicode 중간 앵커는 정상 적용됐고, UTF-16 오프셋 혼동/NFC·NFD 본문 불일치/
없는 출처/추론 주장에 추출 앵커 사용/숫자 변경을 교정으로 위장한 입력은 거절됐다.
검증 전후 전체 export digest도 같았다. 반면 다음 세 입력은 구조 검사를 통과했다.

1. “허용하지 않는다” → “허용한다”를 같은 Idea의 교정으로 제안.
2. “5회 이상” → “5회 미만”을 숫자 변경 없는 교정으로 제안.
3. 조건문에서 “접근을 허용하지 않는다”만 정확히 인용하여 조건을 생략.

이 잘못된 의미 변경은 진단용 validate까지만 실행하고 적용하지 않았다. 구조적
무결성은 통과했지만 의미 검토는 필수라는 **확인된 한계**다. DB에 생성형 모델을
넣거나 몇 개 부정 단어 규칙을 추가했다고 의미 동등성이 보장된다고 할 수 없다.
별도의 의미 검토 근거와 원문의 조건·예외가 연결되어야 한다.

현재 메인 30단계 예제에서도 한 가지 실제 방향 불일치를 확인했다. v3 기획의
`be_2`는 후보→검토→채택→publication과 권한을 요구하지만, 현재 원자는 이전
방향의 “장애 가설 근거 대응 조치의 상태 전이”를 유지한다. DB는 이를 충실히
저장하지만 새 목적에 적합하다고 판정해 주지는 않는다. 기존 원문·역사를 임의로
바꾸지 않고 이 사례를 남겼다. 재사용에는 새 사용 위치에서의 적용 가능성 검토가 필요하다.

## 리뷰 반영과 재현

Grok/Fable의 초기 및 최종 검토에서 자기 일치 질의, 상수 플래그 검사, 부분 인용,
부모 문맥 비용, 대조군 편향을 지적했다. Main은 방해 후보, 문장 창/부모 전용
대조군, 질문 종류별 통계, 엄격한 모델 출력 파싱, 직접 Neo4j 관계 검사를 추가했다.
Grok은 “최신 평가 projection이 이전 레코드를 변경한다”는 초기 지적을 철회했다.
과거 평가 보존과 현재 요약 선택은 별개이며, 과거 이력을 포함하는 재사용 후보도
현재 구성에 자동 채택된 것으로 취급하지 않았다.

```sh
make check
python3 -B -m unittest tests/evidence_test.py tests/integrity_audit_test.py -v
# 새 이미지까지 빌드하는 완전 실행. 생성 모델은 재호출하지 않는다.
make evidence-check
# 같은 런타임 이미지로 실행하려면:
IDEA_DB_SKIP_BUILD=1 IDEA_DB_TEST_IMAGE=idea-db:local \
  IDEA_DB_REPORT_DIR="$PWD/test-results/my-evidence-run" make evidence-check
```

`evidence-check`는 고유 Docker 자원만 사용한다. 결과·실패·stdout/stderr·Neo4j
로그는 삭제하지 않고, 소유한 테스트 컨테이너/데이터 볼륨만 정리한다. 출력 경로를
재사용하지 않는다. 모델 호출 원문 및 메인 DB export는 로컬 `test-results/`에
보존하며 Git에 포함하지 않는다. 공유 가능한 [수치 요약](evidence/20260907-summary.json),
[입력/질의](../tests/evidence_corpus.py), [입력 모델 fixture](../examples/evidence/README.md)는 Git에 포함한다.

최종 로그: `test-results/evidence-run-r5/`. 앞선 `r1`의 잘못된 테스트 링크 종류,
`r3`의 2 MiB 사전 제한 거절과 샌드박스 로컬 포트 제한에 의한 Rust 테스트 실패도
보존했다. 클라이언트가 의존 순서로 패키지를 나누고 마지막에 루트를 적용하도록
수정했다. 이 여러 패키지 전체를 하나의 트랜잭션이라고 주장하지 않는다.

Rust 129개, 신규 Python 검사 17개와 기존 JS 모형 검사가 통과했다. 기본 Rust
실행에서 별도 실DB 취소 테스트 1개는 기존대로 제외된다. 이번 강제 종료는
커밋 완료 뒤의 복구 검증이며, 커밋 진행 중 강제 종료·팀 부하·HA 검증은 아니다.

다음 구현 판단은 원자 수를 늘리는 것이 아니라 **원문 조건/예외의 범위 보존,
변경 목적에 대한 재사용 검토, 예산에 맞춘 문맥 선택**을 기준으로 내려야 한다.
